# App 录制 → Skill 生成 → PI 执行

日期：2026-10-18（Asia/Shanghai）。开发与验收记录。PR #6 已合并（`223b26e`）；本阶段继续打通 App 入口，不用终端专用实验的成功代替 App 实测。

## 用户流程

1. 手机打开 Orulink Control，进入“录制流程”，开始录制并在小红书演示。
2. 回到 App，选择“结束并检查”，检查采集到的操作和固定任务范围。
3. 点击“一键生成 Skill 并由 PI 执行”。离线时请求保存在手机队列，电脑连接后继续。
4. 电脑先按这份录制验证一轮，成功后生成 Skill，再由 PI 复用执行一轮。
5. 回到 App 查看验证、生成、执行及最终结果。失败后先检查手机状态，不自动重放副作用动作。

当前范围仍是搜索“小狮日记”、打开已验证的首篇“当我闯进一个限时48小时的创造营”、点赞、收藏、取消点赞、取消收藏。变更搜索词或帖子、任意 App 流程仍未实现；不把固定演示成功解释为通用手机 Agent。

## 实际控制链路

```text
App 无障碍动作录制
  → 本地检查与用户点击提交
  → 手机持久化队列
  → 电脑伴随服务通过本项目 LAN Android MCP 领取
  → 原始录制解析为有序的候选意图
  → 真实 PI 逐步消费意图，重新观察、定位并验证动作结果
  → 配对示教绑定原始录制摘要，编译 SKILL.md / recipe.json / generation.json
  → 真实 PI 使用新配方执行：本地命中 → 可恢复漂移交给 Jev
      → Jev 请求失败后通过 PI 新观察，再由 DeepSeek 兜底一次
  → 核验完整阶段、目标帖子与最终未点赞/未收藏
  → 安装新 Skill 并原子更新本机 PI profile
  → 回报手机任务结果
```

手机不保存模型密钥。电脑服务读取现有私有 PI profile 和 MCP/模型配置引用。新链路不调用旧 `run_pi_trial.py`、USB 转发或 ADB 控制。

无障碍事件是候选意图，并不自带动作成功证明。实际点赞按钮可能没有文字、描述和资源 ID，因此捕获层需要固定 App 适配器提供有边界的候选证据；数字计数本身不能证明这是点赞。原始记录仍标为未配对验证。执行时重新定位当前控件，不回放历史节点 ID 或坐标；只有实际前后观察通过，才形成可执行配方。

生成器不能只看到搜索词，就丢弃录制、重新运行一份预写完整任务。顺序、目标和候选来源必须匹配；验证运行还必须证明实际消费了录制意图。缺少或歧义的点赞/收藏写入意图必须停止。

2026-10-18 实录暴露了无障碍事件与业务动作的差异：成功示教被 App 记录为 13 个事件，其中有 7 项任务意图、2 次输入框聚焦点击、4 条 RecyclerView 滚动通知，独立“提交搜索”点击未被录到。首个一键任务因此被旧严格解析器拒绝，未生成或发布 Skill。

后续语义方案保留完整原始记录和逐事件摘要，明确区分原录制意图、聚焦证据、列表通知及运行时必要过渡。列表通知不能当成实际滚动手势。只允许在查询已确认正确、尚未进入结果时，由 PI 选择当前唯一“搜索”提交；该动作必须另行记录实际前后观察，标注运行时必要过渡、原始事件序号为空，不能宣称原录制包含它。此方案的实机验收结果见下表。

新生成配方显式标记 `entryStrategy: prepare-feed-v1` 并纳入摘要校验。PI 从桌面或旧页面开始时，只允许打开、返回、等待等准备动作；实际观察到小红书首页后才消费录制步骤。准备动作不伪装成录制步骤，也不提前完成搜索。`preparationRequests` 与 `recoveryRequests` 分开计数，模型总请求仍包含两者；默认旧配方行为保持兼容。

## 任务与文件的边界

- 只有手机本地 UI 可以提交任务。远程 MCP 仅提供领取、心跳和进度回报，不能替换原始录制或凭空创建任务。
- 同一时刻一个任务；重复点击、重复领取、服务重启和租约失效不能自动重跑已经可能改变手机的操作。
- 验证失败不编译；生成失败不复用；复用失败不发布为可用 Skill。
- 最终结果回报失败时，最多进行两次有界投递，总预算 60 秒。新 MCP 会话仅能查询/更新同一任务：ACK 丢失时只读确认，任务仍有效才重传；租约过期或终态冲突时停止。永不为重传结果再次执行 PI、手机动作或发布。持续断线留下私有 `terminal-delivery.json` 的 `unconfirmed` 记录，不能宣称手机已经确认成功。
- 成功配方复制到本机 `~/.local/share/orulink-phone/skills/generated-任务ID/`，文件保留原始摘要，不覆盖不同内容的同名产物。
- 发布保留旧 profile 备份并原子更新 `recipe`。执行期间用户改过 profile 时停止发布，不覆盖用户配置。已启动的 PI 会话仍使用启动时配方，需要重新启动 `pi-phone`。
- 公开手机摘要不包含本机路径、模型密钥、MCP headers 或 claim token。原始录制、截图和 PI 会话只保存在私有作业目录。
- App 的 PI 耗时和模型请求应累计验证与复用两轮；排队、生成和执行到本地落盘的墙钟时间另外记录，不混称模型推理耗时。当前 `wallElapsedMs` 不含最终回报恢复耗时，也不代表手机收到结果的端到端耗时。

## 安装与运行

电脑使用与 `pi-phone` 相同的 profile，默认 `~/.config/orulink-phone/terminal.json`。手机启动本项目 LAN MCP，解锁并保持亮屏。

在仓库根目录运行（`<python>` 为现有 PI profile 中的 Python 绝对路径）：

```sh
<python> experiments/pi-phone-use/companion_service.py install
<python> experiments/pi-phone-use/companion_service.py status
```

临时前台运行可用 `<python> experiments/pi-phone-use/workflow_companion.py --profile ~/.config/orulink-phone/terminal.json`。移除开机服务使用 `companion_service.py uninstall`，保留已录制任务。

电脑服务安装器使用 macOS 当前用户 LaunchAgent；服务依赖安装时的源码目录和 Python 环境，不应在运行期间移除它们。修改 profile 中的 MCP 地址、凭据引用或 Python 环境后重新安装/启动服务，使新配置生效。手机模型判断和动作执行均经 PI，不由伴随程序自行替代决策。

本次构建 APK：`app/build/outputs/apk/foss/debug/app-foss-debug.apk`；版本 `1.12.0-dev.49+223b26e`、versionCode `20009821`，SHA-256 `d805cd780c02ec344ea65e3838d90ca0e1665c11a15c29b351a3807dd58e1c6f`。这是含当前 Android 改动的工作区构建，后缀是构建时基线提交。

更新手机上正在提供 MCP 的同一应用时，Android 可能终止连接并关闭服务或无障碍能力。完成系统安装后，需要在手机打开新版 App、恢复无障碍并启动 MCP；不能把安装请求已发送当作更新成功。此次安装与后续验收不使用 ADB。
